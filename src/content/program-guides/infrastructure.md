Imagine a fictional team training an image classifier on an approved dataset. The job needs more than an accelerator: files must arrive, examples must be decoded, work must be placed, results must be exchanged and heat must leave the equipment. Infrastructure engineering follows that chain rather than treating the rack as a single magic box.

## Follow one workload through the system

Storage holds the dataset and checkpoints. A host-side loader reads and prepares examples. Accelerator compute processes the prepared work. When training is distributed, the network carries the communication required by the chosen strategy. Monitoring should reveal whether the job is waiting for data, communication or compute.

The [NVIDIA DGX SuperPOD reference architecture](https://docs.nvidia.com/dgx-superpod-reference-architecture-dgx-h100.pdf) is a concrete vendor example combining compute, networking, management and storage. Our illustration uses generic equipment; its rack count, cabling and liquid loop are not a deployment specification or a recommendation for that product.

Cooling removes heat generated by powered equipment. The illustration’s copper loop emphasizes that physical constraint; real installations also require power distribution, environmental limits and facility engineering. A logical data-flow diagram cannot replace those engineering requirements.

## Inspect the component that might be holding up the work

For storage, ask whether files are arriving fast enough and whether small-file access dominates. For networking, inspect communication volume, link behavior and collective-operation time. For compute, inspect execution time and resource use under a specified workload. For cooling, examine temperature, thermal limits and the facility’s approved measurements. No single utilization percentage explains all four.

Model weights add another constraint. Seven billion parameters at 16 bits each occupy an ideal 14 GB, or about 13.04 GiB. The calculator shows the arithmetic for other counts and precisions. It excludes runtime allocations, activations, caches, optimizer states and quantization metadata. Lower bit storage also says nothing by itself about answer quality or supported execution formats; [Hugging Face’s quantization guide](https://huggingface.co/docs/transformers/quantization/concept_guide) explains the representation tradeoffs.

## Exercise: profile three stages on a CPU

Use the downloadable standard-library Python exercise below with Python 3.10 or later. It creates a small synthetic dataset, measures reading it, parses its numbers and performs a separate arithmetic workload. Run it three times on the same machine and record each stage. Python’s [performance counter documentation](https://docs.python.org/3/library/time.html#time.perf_counter) explains the elapsed-time clock used.

Do not add the CPU timings to a GPU throughput chart. They measure this local exercise. Change only the dataset size, rerun, and explain which stage changes. File-system caching and interpreter overhead can affect the result; include those limits in your notes.

## Turn the observation into an architecture proposal

Draw the storage-to-loader-to-compute path, the communication path and the checkpoint destination. Name the monitoring evidence you would need before expanding to multiple machines. Include placement, access control, capacity assumptions, an incident owner and a recovery plan.

This is a useful project artifact even without owning a GPU cluster. The illustration is simplified, and the CPU exercise does not validate a data-center design. Start with computer-system foundations, then ask the program team for the current infrastructure curriculum and prerequisites.
