## What if the answer is in your documents?

A model is asked about a procedure updated yesterday. Its parameters may not contain that update. Retrieval-augmented generation introduces another source of information: material retrieved at request time.

## Two pipelines, two sets of decisions

<ResearchStatement kind="interpretation">
  <p>
    The two-pipeline view below is an engineering explanation of a document
    assistant. Ingestion, reranking and citation-handling choices are not
    presented as results from the original RAG experiments.
  </p>
</ResearchStatement>

The preparation pipeline collects documents, extracts text, preserves metadata, splits material into useful units, and builds an index.

The request pipeline interprets a question, retrieves candidates, optionally reranks them, selects context, and asks a model to produce an answer. The answer can include source references for inspection.

## Walk through a failure

<ResearchStatement kind="example">
  <p>
    A reader asks, “How long is the approval window?” The retriever returns an
    old policy because its wording matches the question closely. The model
    summarizes it accurately.
  </p>
</ResearchStatement>

The generation step did its local job, yet the answer is wrong for the current policy. The missing requirement was effective-date handling in the retrieval pipeline. Rewriting the prompt alone will not repair that index.

## Grounding is a measurable behavior

Keep separate questions in your evaluation:

- Did retrieval find the relevant, authorized material?
- Did the selected context include the necessary evidence?
- Does each important answer claim follow from that evidence?
- Do citations point to passages that support the claim?
- Does the system abstain when the evidence is inadequate?

A citation can be real but irrelevant. A fluent answer can combine a correct statement with an unsupported conclusion.

## A practical trade-off table

| Decision               | Benefit                      | Cost or risk                           |
| ---------------------- | ---------------------------- | -------------------------------------- |
| Smaller chunks         | More precise retrieval units | Context can become fragmented          |
| More retrieved context | Potentially broader coverage | Higher latency and irrelevant material |
| Reranking              | A second relevance check     | Another stage to operate and evaluate  |
| Frequent indexing      | Fresher evidence             | More ingestion and versioning work     |

Treat these as design hypotheses. Measure their effects on your own questions.

## What comes next?

Start with a versioned document set and an explicit evaluation set. Log which document versions were selected for each answer without collecting unnecessary personal data.

**Next question:** how should identity, permission checks, caching, and source updates fit around this pipeline? Those are architecture decisions, and they are part of answer quality.
